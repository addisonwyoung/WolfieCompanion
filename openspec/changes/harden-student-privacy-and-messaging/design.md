# Design

## Context

See proposal.md for motivation. The consolidated product decisions supersede the earlier requirement that private students become public to create/join Study Buddies. No such restriction is retained here.

Current implementation anchors for the Stage 3 delta:
- Stage 1/2A/2B migration sources and their recorded local tests establish the settings, directed blocks, contextual identity, mutual DM rules and independent group consent baseline. Preserve these migration files and protections; manual SQL Editor history, not filenames, determines installed state.
- `202611200001_mutual_dm_authorization.sql` still limits messaging additions/candidates to the creator's accepted friends, although consent now uses `allow_group_additions`. `202610250002_group_member_removal.sql` allows creator-only peer removal, lacks self-leave and permits sends below three members.
- `202611190002_student_privacy_authorization.sql` rejects blocked co-member pairings in group/Study admission guards. Stage 3 must change only those admission semantics to actor-target blocks, not loosen DM/general profile blocking.
- Study Buddies currently has initial create/respond/leave only; `studyGroupApi.ts` has no post-creation invitation operation. Creation/acceptance use section context without persisted professor/term context. The UI already obtains professor-aware classmates, which is not sufficient RPC authorization.
- `my_study_groups` exposes member names to pending invitees; pending-safe projection must be corrected while reusing acceptance, availability and task workflows.
- `leave_study_group` transfers owner authority to another accepted member and updates `created_by`. That mutable field cannot serve as immutable actual-inviter provenance. Existing Study ownership/roles remain distinct from ownerless messaging groups.
- `studentPrivacy.ts` already wraps block/unblock and owner-only block listing; profile controls and Blocked Students settings still need integration.
- `NotificationBell.tsx`/`AcademicReminderProvider.tsx` are academic-reminder-specific, including required academic item references. `MessagingNotifications.tsx` supplies message unread badges. Reuse presentation/polling where practical, not the academic schema or fabricated message counts, for private group warnings.

Durable OpenSpec lacks synchronized DM/friendship/Study/group capabilities. Keep historical changes untouched and reconcile them during later sync/archive. This planning revision performs no hosted inspection, SQL execution or implementation; earlier managed-service verification limits remain recorded separately.

## Goals / Non-Goals

**Goals:** Caller-derived database authorization, preserved historical data and voluntary collaboration, coherent contextual visibility, race-safe revocation and admission, reversible preferences, safe manual migration.

**Non-Goals:** Study Buddies messaging, new messaging infrastructure, attachments, moderation/reporting, account-deletion retention redesign, retroactive erasure of delivered data, or hiding shared-group interactions between blocked members. Do not alter eligibility or academic enrollment ownership to implement discoverability.

## Decisions

### 1. Behavior matrix and authorization precedence

| Operation | Private mode | DM preferences | Either-direction block |
|---|---|---|---|
| University-wide search/autocomplete | Public targets across all majors/courses; private targets excluded | No effect | Pair excluded |
| Recipient/Study offering picker | Public eligible targets plus private accepted friends through relationship exception; Study candidates must match the exact verified offering | No effect | Actual actor-target pair excluded |
| Accepted-friend profile | Contextual access retained; field sharing still applies | No effect | Denied outside retained group/history context |
| Existing DM history | Participant access retained; no general profile grant | Read remains available | Read remains available |
| DM send, new or established | New private target needs an authorized existing relationship; private sender may intentionally contact authorized public target | Both preferences must permit relationship | Denied both ways |
| Study Buddies create/invite/accept | Exact verified offering; public candidates/private accepted friends through actual inviter; explicit acceptance | No effect; group-chat consent does not apply | Deny actual inviter-target blocks; third-party blocked co-membership permitted |
| Additional Study invitation | Any eligible accepted member; eight occupied places including pending; immutable actual inviter | No effect | Actual inviter-target check, not all co-members |
| Messaging addition | Eligible active members under All Members, or unrevoked active original creator under Creator Only; public targets/private accepted friends; automatic additions/re-additions | Independent group consent applies to every target | Check actual actor-target pairs; independent third-party admission permitted |
| Existing group participation | Retained contextual identity/history; Study pending previews stay limited | DM settings do not apply | Retained interaction; only outgoing blocker receives private warning |
| New messaging-group send | At least three eligible active members; retain smaller groups read-only | DM settings do not apply | Shared blocked co-membership does not by itself disable sends |
| Group leave | Always voluntary for eligible members, including private members and creator | No effect | No effect |
| Personal academic features | Unchanged | Unchanged | Unchanged |

All operations retain existing caller/account eligibility. Active messaging-group membership authorizes display name, profile picture and basic identity for all active co-members regardless of friendship or private status. This group-specific picture audience is separate from general/classmate picture sharing; it does not unlock other optional fields, raw avatar paths, full profiles, emails or schedules. Historical message attribution remains within authorized message history after departure. Pending Study Buddy invitations expose only safe invitation metadata, not member content.

### 2. Separate policy predicates and owner settings

Add `is_private boolean`, constrained `dm_permission` text (`eligible_students`, `friends_only`, `no_one`), and `allow_group_additions boolean` to owner settings. Keep optional sharing independent. Add directed block rows keyed by blocker/blocked, self-block denial, and reverse-lookup indexing. Only owners can inspect their block lists; narrowly granted block/unblock RPCs perform compound mutations.

Keep trusted eligibility and offering membership helpers independent of privacy. Implement separate predicates for general discovery, contextual profile access, block existence, verified shared offering, DM sendability, and group admission. Do not change `private.is_eligible` or make a private student fail enrollment membership checks. Prefer shared predicates over copying privacy clauses into every RPC, while preserving caller-derived policy execution and empty search paths for security-definer functions. Anonymous clients and arbitrary caller-id helper execution remain denied.

### 3. Mutual DM permission and established-contact semantics

For every new insertion: both accounts eligible, no block, authorized contact basis, and both preferences permit the pair. `no_one` denies all exchange; `friends_only` requires current accepted friendship; `eligible_students` accepts established thread, accepted friendship, pending friend request, or verified current shared course/section/professor. A supplied UUID or directory listing alone does not establish contact. Private first-contact recipients require accepted friendship or a pending request they initiated to the caller; a request initiated by the caller does not authorize contact with a private recipient. This exception is DM-only and never overrides preferences, blocks or eligibility, or grants general discovery/profile/avatar access. A private sender may intentionally message a public authorized classmate, disclosing minimal sender identity in that conversation.

An established thread remains a contact basis after course/friendship loss, but cannot bypass either preference or blocking. History, inbox and read positions remain participant-authorized even when sending is denied. Keep one thread per pair and original IDs. Contact-state and send use the same predicate; return safe reason categories (own preference, friendship required, contact unavailable) without revealing someone else's block direction/private state. The blocker can see their own block reason. Existing read-only chats remain openable.

Mutual authorization was chosen over incoming-only to avoid unanswerable outbound messages and make read-only a conversation-wide state. Explain this in settings. Rechecking the recipient only would contradict the approved mutual model.

Retain current text limits, server sequence assignment and exact request retries. A replay confirming an already stored message is not a new send; it may acknowledge only the same participant-owned message without inserting, advancing activity, or granting extra data. A previously uncommitted request must pass current authorization. Never auto-resend after unblocking or a setting change.

### 4. Reuse Study Buddies invitations with authoritative offering and capacity

Preserve course -> classmates -> group name -> create/send invitations, and reuse the existing pending/accepted workflow for an additional-invitation action available to every eligible accepted member. No owner-only invitation role or Study messaging is introduced. Public classmates need no friendship; private candidates require the actual inviter's accepted friendship. Neither shared enrollment nor another member's friendship exposes private non-friends.

Persist the group's authoritative course, section, professor, semester and academic year through the smallest suitable verified-offering reference/context. Use existing verified offering helpers for both caller/candidate checks; a section-only argument, planner course, pending/rejected enrollment or frontend filter is not authority. Freeze the group context across ownership transfer; do not silently roll the group into another professor or term. Do not bind group lifetime to a creator's mutable/deletable enrollment row through cascading deletion. Accepted members retain existing access after course/privacy changes, while new invitations/acceptance must satisfy the current verified offering rules.

Count all accepted memberships plus verified, unexpired pending invitations against eight places, including the creator. Initial create allows one to seven invitees; additional selection is bounded by remaining capacity. Reuse the group row lock for create/invite/accept/decline/leave transitions, recheck the actual inviter's accepted membership after locking, then follow the compatible canonical pair/profile lock order for target checks. Reserve pending places atomically; acceptance converts the existing reservation, decline releases it, duplicates/retries cannot consume another place and invalid batches do not partially apply. This avoids an additional reservation system.

Record immutable actual-inviter identity per invitation, derived from the authenticated sender rather than a client-supplied owner/inviter ID. Store it separately from mutable Study ownership, without a cascading dependency on the inviter's removable membership row. A duplicate pending invitation must not replace its inviter; a genuinely new invitation after decline records its new actual actor. Ownership transfer alone must not rewrite/cancel pending invitations. Acceptance revalidates target eligibility, exact offering, verified issuance, the 168-hour deadline and the recorded inviter-target block pair; privacy/friendship changes after issuance alone do not revoke the invitation, never blocks against every accepted co-member. Preserve original attribution after inviter/owner departure; apply the finalized departed-inviter rule below and do not fabricate missing legacy provenance.

Extend the existing API/Study UI with an accepted-member invitation action and occupied/remaining capacity, reusing candidate selection and accept/decline components. Pending previews expose only safe group/offering metadata and minimal actual-inviter attribution, not the roster, availability, study roles, tasks, private warnings or full profiles. Fix the current roster leak at the RPC/projection boundary and verify direct/event access too. Declines and target-authorization failures remain generic.

Keep accepted membership, existing tasks/notes/authorship and the remaining group's data when the owner leaves; reuse existing deterministic Study ownership succession and voluntary member leave. Remove active membership/availability on departure. Two remaining members do not trigger deletion or a chat-style send threshold. Preserve the existing final-member deletion allowance, without new Study membership-history, archive, contribution-recovery or messaging infrastructure. The finalized pending-only deletion and legacy provenance rules are recorded below.

### 5. Member-managed messaging and recipient selection

Preserve `GroupPicker.tsx` layout, optional name, selections, retry behavior and paging. Change labels from friends to students. Friend suggestions are convenience ordering, not authorization. Query bounded public-student results university-wide (no major/course/section/friendship filter), union with the caller's authorized private accepted friends, deduplicate by UUID and paginate deterministically. Do not fetch all private profiles and filter in React. Stage 2A widened `friend_directory` to include public accepted friends; still verify that any reused projection also supplies authorized private accepted friends, supports bounded paging and never makes group identity general discovery.

Messaging groups have `all_members` (default, including existing groups) and `creator_only` addition permissions. An eligible active member may add in all-members mode; only the original active creator with unrevoked creator privileges may add in creator-only mode. The creator selects this at creation and may change it only while active and before their first departure. No administrator/moderator/owner transfer is introduced. No friendship is created by group admission; no DM preference gates participation. Preserve two selected recipients plus creator for creation (3 initial people), at least one for later additions, and 50 active members. Keep independent group-addition consent, initialized true independently of the old boolean in Stage 1 and preserving subsequent choices; disabled consent rejects every addition and re-addition, without affecting existing participation.

All additions and re-additions are automatic, including private friends and students who previously voluntarily left. On every addition revalidate adding caller's eligible active membership (or deliberate creation), recipient eligibility, public visibility or accepted friendship for a private target, `allow_group_additions`, capacity, and bilateral blocks between the authenticated adding member and each selected target. No pending messaging invitations, accept/decline operations, rejoin requests or departure-reason checks are introduced. Former members cannot self-rejoin; an eligible active member must add them. A private request to a member remains an ordinary DM subject to mutual preferences and blocking. An independent third party may add students who have blocked one another; blocks solely between targets or other co-members are not admission vetoes. Existing memberships are never removed automatically. Change both the RPC and Stage 2A admission trigger so they agree on actor-target authorization; a privileged insertion must not omit or forge the trusted actor. Keep atomic whole-batch rejection rather than silently excluding selected students. Use one generic target-unavailability explanation across blocking, privacy, consent and other authorization failures, including picker disabled-state reasons; do not return a restriction category or blocking party.

### 5a. Three-member threshold for genuinely new group messages

Keep three eligible students at messaging-group creation and a 50-member maximum. For each genuinely new message, under the same group lock as additions/leaves, recheck caller active membership and count at least three currently eligible active accounts. Do not count ineligible accounts merely because membership rows remain; DM preferences and co-member blocks alone do not reduce the count. Retain membership/history and normal entitled reads if the count falls below three. Authorized additions and self-leave remain available so a small group can recover or be left voluntarily.

Expose only safe sendability and a generic disabled-composer reason through detail/contact APIs and Messages UI. Do not reveal whose eligibility changed. Restoring three eligible members re-enables sending without automatic draft delivery. Keep exact committed retries non-writing and verify their audience/sequence floor; a stale retry must not restore departed membership or pre-readdition history. Normal RPCs and privileged insertion boundaries must enforce equivalent new-message restrictions.

### 6. Simple departure and message-history boundaries

Reuse the current `group_members` active row and `joined_after_sequence` floor. Under the shared group lock, self-leave deletes the active membership/read position and revokes access; addition inserts a new active row with a fresh floor at the group's current last sequence. This excludes pre-join messages and absence messages on every return, without restoring prior-tenure messages, matching the existing readdition mechanism. Apply the floor consistently to direct SELECT RLS, RPC history/catch-up, inbox previews, unread and realtime. No membership episode table, leave-reason tracking or separate historical membership infrastructure is required for this rule. Add infrastructure only if implementation evidence demonstrates a concrete authorization need; do not add it for retention or acceptance policy.

When the final member leaves, make the messaging group inactive and retain its messages without active client access. Deny messages/additions through every current/legacy path; a stale receipt or creator ID cannot reactivate it. Any active member can leave at any size; no one can remove another. Retire creator-only peer-removal authority without adding owner/manager/admin roles. Preserve creator attribution. Atomically latch creator departure permanently and switch addition permission to all-members before deleting the creator membership; later re-addition cannot restore setting authority or creator-only addition rights. Use two small group columns rather than an ownership/lifecycle system; an empty retained group has no active client access and cannot be revived by creator metadata. Recheck membership after locking to serialize sends/additions/leaves, and retain exact retry behavior without resurrecting deleted memberships. Clients clear revoked group data and ignore late responses.

### 6a. Group-scoped identity and picture delivery

Add or adapt a narrowly scoped group identity projection and backend picture route. Require caller eligibility and active membership in the supplied group, and active target membership for current member-picture access. Resolve only the target's current saved picture server-side; return no reusable public/signed URL, raw storage path, full-profile payload or unrelated private fields. Revalidate in the service-role resolver as well as the backend request check and use private no-store responses. No general/private-nonfriend discovery is granted by group membership. Missing pictures use the existing initials fallback. The group-specific picture audience does not require enabling general/classmate picture sharing. Explain this audience before addition/participation in privacy notices.

Historical messages retain appropriate sender attribution after departure without requiring membership history or profile snapshots. Remaining authorized readers can retain sender identifier/display-name attribution, but historical sender IDs do not authorize current private-picture or full-profile retrieval after target departure. A new group member still cannot read pre-join messages to discover earlier authors. Existing shared blocked members retain group-context identity/picture interaction under the documented shared-group exception; direct messaging and direct actor-target blocked additions/invitations remain prohibited; independent third-party admission remains subject to its other rules.

### 7. Blocks, atomicity and legacy entry points

Block RPC atomically inserts the directed block, deletes accepted friendship and invalidates pending friendship requests. Unblock removes only the caller's direction, restores nothing, and leaves a reverse block effective. Block/unblock controls belong in authorized profile/DM views and an owner-only block management view so a hidden target can still be unblocked. No notification announces a block to its target; generic unavailability can still allow inference. Preserve shared groups and historical identity. Deny direct adding/inviting actor-target blocks in either direction, while allowing independent third parties to admit blocked co-members under the other privacy/eligibility/consent checks. For Study acceptance, use immutable invitation provenance rather than the current owner or the accepting invitee as a substitute admission actor.

Use canonical pair locks shared by block, friend send/accept and DM writes; lock profile rows in stable order for settings/admission. Group mutations share the group lock and recheck membership after acquiring it. Define one lock order for combined group/profile/pair operations, then test concurrent block, settings, accepts, leaves and sends for deadlocks and stale authorization. The implementation must establish serialized order: revocation ordered before a mutation's authorization point prevents its commit; earlier committed messages cannot be recalled.

Audit function overloads and ACLs from the final migrated catalog. Includes directory and discoverable/friend/classmate profiles; course/section/professor discovery, recommendations and relationship projections; friend send/respond; both avatar resolver families; Study Buddies create/respond/list; DM state/send/history/inbox; group candidate/create/add/leave/detail/history/send, eligible-member send counts and group identity/picture access, plus retired peer-removal signatures; Study additional invite/candidate/accept/capacity/provenance and owner-only warning/acknowledgement paths; combined inbox/unread and table/event access. Retire unsafe legacy signatures or make them equally restrictive. Security-definer RPCs bypass ordinary RLS, so table policies alone are insufficient. Service-role avatar resolvers must recheck authorization and current sharing, not merely trust earlier Express checks. Keep raw profile ownership and denied direct message writes intact.

### 7a. Block controls and private shared-group warnings

Reuse the Stage 2A block/unblock RPCs and `studentPrivacyApi` for profile actions and a Blocked Students section in privacy settings. Only the owner can list/manage their outgoing blocks, including targets hidden from discovery; do not fetch unrestricted private profiles to label them. Unblock removes only that actor's direction and restores no friendship. Do not modify Stage 2B mutual DM authorization or expose incoming block direction.

For each active messaging member or accepted Study member, compute warnings from that viewer's own outgoing blocks intersected with the authorized current roster. If Alice blocks Bob, only Alice receives the warning; Sally's ability to admit both does not authorize her to inspect that relationship. Pending Study invitees see no member-only warning. Shared roster/message payloads, group events and peer-readable counts must not carry viewer warning flags or block direction.

Provide an owner-only notification projection plus a dismissible contextual banner and leave action in Messages/StudyGroups. Reuse the existing bell/list presentation and visible polling/focus lifecycle where feasible, but do not store privacy warnings as academic reminder occurrences requiring academic-item references, or fabricate message unread counts. Persist only minimal owner-scoped acknowledgement/delivery state keyed by viewer, group, blocked student and block episode. Refresh/reconnect within that episode must not repeat notices; a new block episode or membership episode may rearm a warning, without changing authorization. Warnings remain private to the outgoing blocker. Couple a recipient to the session on both read and acknowledgement; never accept a forged warning owner. Dismissal changes neither block nor membership. Retain an active-membership check on navigation from a saved notification and clear stale warning data on departure/account replacement. The approved episode reset rule supersedes the previous relationship-wide notification deduplication proposal. Warning implementation is outside Stage 3A.

### 8. Client, notifications and acceptance testing

Use existing polling/focus/event infrastructure, with immediate actor-side invalidation after preference, block, invitation or leave actions. Re-fetch permission state on focus/reconnect and messaging's visible polling; no peer-readable profile/block publication is required. Clear revoked directory/profile/picker results and group caches; reject late responses across contexts/accounts. Render retained DM history with safe read-only explanations and preserve unsent drafts without automatic delivery. Only Study Buddy invitations have pending state; group chats have no pending admission UI. Never fabricate unread message counts from membership changes.

Denied writes create no new message event, preview, unread increment or notification. Keep pre-existing DM unread/read positions as historical state; do not manufacture new alerts upon restriction/unblocking. Shared-group notifications continue for entitled members, including blocked pairs. Existing RLS supports authorized historical DM reads and membership/post-join group reads; do not add a blanket block filter that erases retained history. Verify deployed subscriptions with unrelated users and nonmembers, plus pending Study Buddy invitees, not just mocked client filters.

## Risks / Trade-offs

- Shared-group interactions permit indirect contact between blocked students -> explicit notices, voluntary leave, direct actor-target restrictions plus blocker-only warnings; no claim of full isolation or impossible-to-infer block relationships.
- Historical messages and delivered pictures retain identity -> explain that privacy is not erasure; Study Buddy data is preserved only while its group exists, without recovery/archives.
- Study Buddy pending preview leaks -> restrict pending projections and warnings; retain only safe actual-inviter/group/offering metadata.
- Concurrent additional invitations exceed eight places or replace inviter provenance -> group-row serialization, pending reservations, immutable per-invitation actor and retry/duplicate tests.
- Legacy Study rows lack offering/inviter evidence -> preserve accepted data, inventory ambiguity and stop short of guessed authorization.
- Private warnings leak direction or repeat on reconnect -> caller-scoped RPC/RLS, owner-only delivery/acknowledgement and explicit reset decisions.
- Legacy course-level checks allow pending/rejected enrollment -> replace new-contact use with verified offering checks and audit every surviving overload.
- Automatic admission racing consent, leave or block changes -> common locks, bounded retries, stable receipts and current active-membership rechecks.
- Sequence floors drifting across projections -> use the same active-membership floor for RPCs, direct RLS, previews, unread and events; no departure history is needed.
- Cached UI may briefly show previously delivered identity -> clear on known revocation and refresh; server remains authoritative at every read/write boundary.
- Old specs describe superseded behavior -> explicit new contracts, prerequisite reconciliation at later sync; no historical artifact rewrites.

## Finalized Study Buddies and warning decisions (later stages)

Preserve legacy invitations and accepted memberships; record the actual inviter immutably for every new invitation and never fabricate a missing historical inviter. A missing legacy identity must remain explicitly unknown, not inferred from a transferred owner. Later Study implementation must document how legacy acceptance can be verified when original provenance is unavailable, without claiming an original-inviter block check was performed against an invented identity.

Pending invitations may remain actionable after their actual inviter leaves or becomes ineligible, provided the group exists and the invitee remains eligible. Require verified issuance, an unexpired deadline, current recipient/offering eligibility, original-inviter blocking and capacity; do not reimpose current friendship/privacy after issuance; do not require the original inviter to retain active membership/eligibility merely to honor the invitation. Preserve original inviter identity after ownership transfer/departure. When no accepted members remain, delete the Study group and invalidate pending invitations, with generic unavailable handling; durable private notification delivery is deferred to Stage 3C. Preserve existing deterministic ownership succession if accepted members remain.

Warning delivery is private to the outgoing blocker and deduplicated by viewer/group/blocked student/block episode. A new block or membership episode permits reappearance. Dismissing a notification/banner changes neither authorization nor membership. These are approved specification decisions only: Study, warnings, bell integration and Block/Unblock UI are not implemented during Stage 3A.

## Stage 3A implementation boundary

Implement only messaging addition permissions, automatic admission with actor-target blocks, self-leave, permanent creator departure, minimum-three-eligible-member sending and their existing React adapters/UI. Retain Stage 1-2B SQL unchanged and use one incremental migration. The existing creator checks are limited to additions/candidates/removal and the UI; history/unread/avatars already use membership. Two group columns (addition permission and a permanent creator-departed latch), existing mutation receipts and deletion of active memberships suffice; no ownership transfer, membership-history table or elaborate group lifecycle is required. Keep abandoned group rows/messages without active members and deny all former-member access under the existing floor model. Remaining active members preserve authorized history; re-additions receive a new floor rather than restored previous-tenure access.

## Stage 3B implementation contract

Reuse course_enrollments and private.resolve_current_semester without modifying semester_calendar, calendar helpers or academic-year infrastructure. Snapshot normalized course/section/professor/semester/integer academic_year from a verified creator enrollment into new Study group context fields; do not cascade group lifetime with mutable enrollment rows. A stored term must match the existing current-term resolver for new admissions; accepted collaboration is independent of ongoing enrollment, privacy or co-member blocks.

The supplied pre-3B inventory contains one CSE 416 group with null section, four accepted members, one task, eight availability rows and no pending invitations. Preserve all rows and mark no inferred offering context. Its new admissions remain unavailable until explicit reviewed reconciliation. Nullable invitation provenance means legacy unverifiable pending rows remain non-acceptable and non-reserving; never fabricate an inviter or grant a fresh seven-day window from legacy timestamps.

Reuse pending/accepted membership rows. Store authenticated actual inviter, fresh invitation UUID and trusted issued_at only for newly verified issuance; expose expires_at as issued_at plus interval '168 hours'. Retain expired pending rows until recipient dismissal or a fresh authorized replacement. A replacement may update only a non-accepted expired/unverifiable row and must create a new generation; never replace active pending or accepted rows. Decline/accept must name the generation, with a guarded null-generation dismissal for legacy rows. Retire unsafe group-id-only response/section-only creation entry points. No membership-history ledger is introduced.

A minimal private Study operation receipt store binds actor/request UUID to payload and issued outcome. It survives invitation replacement/deletion and group deletion sufficiently to reject stale replays; it must not cascade with membership/group rows. Replay never renews expiry, changes inviter or resurrects a group. Client retries freeze the full submitted payload and request identifier. Conflicting request reuse fails generically. Reuse the existing group-row -> canonical sorted pair -> sorted profile lock order and take a fresh trusted clock reading after waits; do not authorize expiry using transaction-start time. Count accepted plus verified unexpired pending only. The active reservation remains during temporary blocking/ineligibility until decline/expiry. Atomic batches never silently omit targets.

Private-student visibility applies at issuance only: public targets or the actual inviter's accepted private friends, exact verified offering and actor-target bilateral block checks. Acceptance is session-bound to the recipient, group and generation and checks verified issuance, account eligibility, deadline, exact current offering, capacity/active group and original inviter blocks. Inviter departure/ineligibility or later privacy/friendship changes alone do not invalidate acceptance. Third-party blocked co-membership remains permitted; DM and regular group chat rules are unchanged.

Pending/expired/unverifiable recipients see safe invitation metadata only, never owner/roster/availability/task payloads. Accepted members see accepted identities and active pending counts; only an authorized actual inviter receives minimal outgoing pending identity metadata for management. Shared-resource mutations serialize with membership departure and recheck accepted membership under the same group lock; preserve existing owner/author safeguards. The UI reuses StudyGroups layout and scoped candidate selection, shows server-derived pending/expired/unavailable states and expiry times, preserves unsaved academic drafts, and rejects stale responses on account changes. Durable notifications, warnings and bell integration remain Stage 3C.
