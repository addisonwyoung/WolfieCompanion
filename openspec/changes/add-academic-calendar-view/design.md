# Design

## Context

See proposal.md for motivation. On `main` (`13c780e`), `AcademicPlanner.tsx` owns a single `useAcademicItems` collection, shared course/type filters, a boolean Pending/Completed filter, agenda rendering, and Add/Edit/Delete modal state. `openEdit(item, trigger)` already accepts an item and return-focus trigger. Confirmed mutations replace the saved row in the common hook. Items have a required `due_date` string, nullable `due_time`, four types, and completion timestamps. The adapter loads all owner-visible items and RLS enforces private saved-course associations. `AcademicItemDialog.tsx` already covers dirty drafts, failure retention, completion editing, and native modality. Current return-focus fallbacks search agenda checkboxes/groups and must become aware of the active tab. Existing tests include a synthetic native Chrome fixture and campus midnight cases.

## Goals / Non-Goals

**Goals:** Provide a second rendering of the same saved collection; reuse the proven editor; retain filtering and month context; place dates without browser-zone shifts; ensure a usable phone calendar and logical focus after rescheduling.

**Non-Goals:** External calendar sync/export, class meeting schedules, peer items, reminders/email, drag-to-reschedule, recurrence, week/day time-grid views, empty-date quick creation, separate calendar storage, and new deletion controls in calendar entries. Existing Agenda deletion remains available; Calendar's editor can change completion as today.

## Decisions

1. **Keep planner state and persistence centralized.** Add an `agenda | calendar` presentation state to `AcademicPlanner`, with a presentational `AcademicCalendar.tsx` receiving filtered items, courses, campus today, viewed month/selected day, busy state, and an edit callback. Both tabs use the existing hook's saved rows and pending-write guard. No additional load on tab/month switches and no schema/server work. Separate loaders or copied event records would risk duplicate/stale items after edits.

2. **Separate presentation and status controls.** Add a real tablist above the shared filters with associated tab panels and roving tab focus/Left/Right/Home/End keys. Agenda remains the first/default tab, preserving its existing boolean status selection. Calendar gets `all | pending | completed`, default all. Share course/type state, retain calendar month/day and each tab's status state in planner memory, and close agenda action menus on a tab switch. Preserve view context across existing app navigation while the account workspace remains mounted; reset on reload or account teardown. This gives Calendar all personally added items without changing Agenda's established default behavior. A shared completion toggle was rejected because entering from Pending would silently exclude completed items.

3. **Derive a month model from calendar components, not local instants.** Add pure helpers for campus date keys, Sunday-first month cells, bounded month navigation (years 0001–9999), selected-date normalization, and date-key item grouping. Keep `due_date` as the grouping key; use UTC only as a weekday/arithmetic anchor with full-year setters to avoid JavaScript's 0–99 year constructor adjustment. Pad date keys and preserve leap rules. Reuse `compareItems`, `itemGroup`, campus zone, and the existing clock refresh. Current month defaults to campus today; explicit navigation picks the first day (or today when navigating into today's month); Today picks campus today. Midnight refresh changes highlight/status, never the browsed month. Do not parse stored deadlines through browser-local date formatting. No calendar library is necessary for this bounded month-only feature; avoid adding a large dependency or an independent timezone implementation.

4. **Render every date and make dense days usable.** Desktop uses a seven-column month table with named weekday headers, date cells, current-day indication, and full lists of item buttons. Padding cells outside the selected month are inert; items appear once on their own month. Each event shows title/course/type, optional readable campus time, and textual completion/overdue state. Allow wrapping and vertical growth rather than silently capping event counts. On narrow screens use the same compact month grid with selectable dates and counts, with the selected day's full event list below it. Retain the selected day in planner state so a responsive layout change keeps context. Hide the alternate event rendering from layout, accessibility, and tab order. This avoids cramming full titles/touch targets into 45px phone day cells. Use native table semantics and ordinary buttons; do not claim an ARIA grid without implementing its full keyboard contract. Date selector buttons expose the full date and count; every item action has a full accessible name.

5. **Open the existing modal directly and preserve confirmation semantics.** Calendar item buttons call existing `openEdit(item, event.currentTarget)` and retain the original UUID. Extend return-focus handling to prefer the still-visible initiating item button; if moved/filtered, focus the selected date button or named calendar heading. Keep month/filter selection after saving even if the item moves elsewhere; report success through existing accessible feedback. On phones, an edited item whose date moved requires selecting the new date/month to view it again. Add item keeps existing course prefill and required-date entry from either tab. A calendar-specific editor or optimistic event relocation would duplicate validation and undermine failure semantics.

6. **Preserve account and modal boundaries.** No new localStorage for private events or drafts. Retain account-keyed planner mounting, generation checks, and existing modal teardown. Modal background inertness blocks changing tabs/month while editing; external auth changes still clear all private state immediately. Keep no-courses/loading/error states shared; for a successful empty month show the navigable grid plus contextual no-items text, rather than replacing navigation with the agenda empty panel. Use shared mutation results so edits/deletes/completion from Agenda are reflected on the next Calendar render.

## Risks / Trade-offs

- Crowded months can be tall on desktop → allow natural vertical scrolling and render all entries; phone selected-day list keeps touch targets usable without a hidden overflow cap.
- Rescheduling removes the opener from the current view → resolve focus after the React commit and use calendar-specific visible fallbacks; never focus a hidden agenda control.
- Date constructor and browser-zone bugs → test leap years, December/January, years below 100 and supported endpoints, DST transitions, date-only null times, and a browser outside America/New_York.
- Distinct completion selectors may confuse users → label them clearly and document Calendar's All default while preserving each tab's selection.
- Existing UI tests identify headings/status buttons globally → scope new assertions to panels and retain agenda regression coverage rather than weakening it.

## Migration Plan

Client-only release using the existing academic-items migration already required on main. Implement helpers/tests, tabs/calendar, editor/focus integration, documentation, then run the client suite/lint/build and synthetic Chrome checks at desktop and 375px. No database migration or new secrets. Roll back the client release to remove the Calendar presentation while preserving all saved items and existing Agenda editing. Real-account acceptance should confirm the same saved item across reload and both tabs; synthetic checks must be reported separately.
